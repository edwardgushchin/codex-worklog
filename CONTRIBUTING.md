# Contributing to Codex Worklog

Thank you for helping improve Codex Worklog. Contributions are welcome for the hook runtime, lifecycle contract, history-inspection skill, tests, documentation, accessibility, and marketplace packaging.

## Before You Start

- Read and follow the [Code of Conduct](CODE_OF_CONDUCT.md).
- Search [existing issues](https://github.com/edwardgushchin/codex-worklog/issues) and [discussions](https://github.com/edwardgushchin/codex-worklog/discussions).
- Use the [support guide](SUPPORT.md) for usage questions.
- Report vulnerabilities privately according to [SECURITY.md](SECURITY.md).
- Open an issue before a breaking lifecycle, file-format, privacy, or installation change.

## Development Setup

Requirements:

- Python 3.10 or newer;
- Git;
- a current Codex CLI for optional local marketplace smoke tests.

Fork the repository in GitHub, clone the fork URL shown there, and run the local checks:

```bash
git clone <your-fork-url>
cd codex-worklog
python3 -m unittest discover -s tests -v
python3 scripts/validate_repository.py
```

The runtime intentionally uses only the Python standard library. Do not add a runtime dependency without prior maintainer agreement and a documented portability, security, and maintenance justification.

## Design Contract

Changes must preserve these defaults unless a reviewed proposal explicitly replaces them:

- worklogs live under the original session `cwd`;
- each Codex session has its own append-only Markdown file;
- state-change entries are derived and appended by `Stop`, never delegated to the
  active agent;
- acknowledgement, inspection, context-recovery, verification-only, and
  explicit no-change outcomes create no timeline entry unless they establish a
  cause, decision, transition, or new blocker;
- prompts, transcripts, tool inputs, and tool output are not copied;
- `PLUGIN_DATA` contains only minimal session metadata and hashed identifiers;
- the exported `worklog` skill only inspects history on a relevant request,
  never maintains it, and lifecycle hooks inject no maintenance context;
- the plugin does not modify project `.gitignore` files;
- missing runtime support or unsafe paths are reported instead of silently redirecting data;
- `Stop` never creates a continuation prompt to request a write.

See [Architecture](docs/ARCHITECTURE.md) and [Threat Model](docs/THREAT_MODEL.md).

## Making Changes

Create a focused topic branch from the latest `main`. Keep commits reviewable and limited to one coherent concern.

- Write code, comments, commit messages, and primary documentation in English.
- Preserve Python 3.10 compatibility and Windows, macOS, and Linux behavior.
- Use `pathlib` and the standard library for runtime code.
- Add or update tests for every behavior change and regression fix.
- Update both READMEs when installation or user-visible behavior changes.
- Update `CHANGELOG.md` under **Unreleased**.
- Never include worklogs, plugin cache contents, credentials, tokens, transcripts, or generated bytecode.
- Do not change the stable plugin or marketplace identifier `codex-worklog`.

## Testing

Run the narrowest relevant test while iterating. Before opening a pull request, run:

```bash
python3 -m compileall -q plugins scripts tests
python3 -m unittest discover -s tests -v
python3 scripts/validate_repository.py
```

If Codex is available, test from a temporary marketplace registration and a temporary workspace. Do not overwrite an unrelated installed marketplace or leave test worklogs in another project.

## Commits and Pull Requests

- Use an imperative English subject; Conventional Commit prefixes such as `feat:`, `fix:`, `docs:`, and `test:` are encouraged.
- Link the related issue with `Fixes #123`, `Closes #123`, or `Refs #123` when appropriate.
- Complete the pull request template.
- List exact verification commands and operating systems used.
- Describe privacy, compatibility, and migration impact.
- Keep generated files, unrelated formatting, and personal environment changes out of the pull request.
