## О проекте

Codex Worklog автоматически ведёт локальный смысловой дневник каждой задачи Codex, дописывая результаты работы в Markdown-файл рабочего каталога, привязанного к текущему ходу:

```text
<session cwd>/.dev-diary/YYYY/MM/YYYY-MM-DD.md
```

Активная модель пишет полноценные рабочие блоки по контексту фактически
выполненной работы. В каждом шесть разделов: контекст, хронология, изменения,
решения, проверки и следующие шаги. Вместе с результатом сохраняются
неудачные кандидаты, отвергнутые альтернативы, точные результаты проверок,
ссылки на доказательства и оставшаяся работа. Подтверждения и повторение
истории отдельной записи не создают.

Python проверяет, очищает и сохраняет структурированное содержание.
`submit` сохраняет завершённые блоки до подтверждения успеха, не ожидая
события завершения задачи.
Параллельные сессии используют один дневной файл, сохраняя собственные
идентификаторы записей и ссылки на сессию.

Проекту не нужны собственный `AGENTS.md`, Git, MCP-сервер, внешний сервис, учётная запись или API-ключ.

## Как это работает

Плагин объединяет команду сохранения, пять lifecycle hooks и один узкий skill для просмотра истории.

| Этап | Назначение |
| --- | --- |
| `SessionStart` | Создаёт приватное состояние, привязанное к исходному `cwd`; пустой дневник не создаётся. |
| `UserPromptSubmit` | Передаёт самодостаточную инструкцию автору и точную команду установленного `submit` для текущего хода. |
| `PreToolUse` | Регистрирует автоматические продолжения; повторяет текущую команду и краткую схему, пока ход не записан, а после сжатия контекста восстанавливает полную инструкцию. |
| `submit` | Проверяет блоки, сохраняет подготовленные данные для восстановления и атомарно записывает дневник до подтверждения успеха. |
| `Stop` | Повторяет запись подготовленных, но ещё не сохранённых блоков; новый текст не сочиняет. |
| `SessionEnd` | Повторяет запись оставшихся подготовленных блоков; дополнительный текст не сочиняет. |

Перед завершением работы модель передаёт JSON через stdin в предоставленную
команду `worklog.py submit --data … --session … --turn …`, выполняя её из
рабочего каталога, указанного в инструкции текущего хода. Допускается до восьми самостоятельных блоков
либо явная причина пропуска. Модель не выбирает путь дневника и служебный
маркер. Схема и ограничения описаны в [архитектуре](docs/ARCHITECTURE.md).

Если Codex меняет рабочий каталог задачи между ходами, следующий запрос или
локальный инструмент привязывает новую работу к новому проекту. Старые записи
остаются на месте; подготовленные блоки прежнего проекта ждут возврата задачи
в него. Команда отправки не может сама выбирать или менять каталог записи.

Для значимой работы ответ содержит `recorded: true` и `staged: false` только
после сохранения дневного файла. Ошибка записи завершает команду с ненулевым
кодом без ложного успеха; подготовленные блоки остаются для повторной попытки
командой или hook. Явный пропуск подтверждается отдельно и не создаёт запись.

В задаче с режимом `workspace-write` shell может не иметь права записи в служебный `PLUGIN_DATA`, даже если дневник проекта доступен. Инструкция автору предписывает запросить точечное разрешение на выполнение именно команды `submit`. Если разрешение недоступно, команда явно сообщает об ошибке; повтор в той же песочнице не поможет.

Лимиты текста действуют и после очистки. Если маскировка увеличила пункт сверх
лимита, `submit` отклоняет его до постановки в очередь и просит сократить текст.
Прежние подготовленные данные сохраняются; доказательства молча не обрезаются.

В `PLUGIN_DATA` хранятся проверенные пути, идентификаторы, время, язык и
очищенные блоки до сохранения. Hooks не читают transcript и не извлекают
содержание из финального ответа. При отсутствии корректного payload `Stop`
показывает предупреждение и пропускает запись, без выдуманного результата
и дополнительного хода ради дневника.

Дата файла определяется временем отправки payload. Приоритет языка:
язык сессии от хоста, язык автора, явная настройка, локаль ОС. Сохраняются
точные команды, численные результаты, полные SHA-256, безопасный Markdown и
относительные пути доказательств. Абсолютные пути внутри рабочего каталога
преобразуются в относительные. Git status автоматически не собирается:
исходное состояние, дельты и commit автор добавляет только при их значимости.

Пример записи:

```markdown
## 2026-09-04 16:51 +03:00 — Потребители переведены на проверенное назначение

### Контекст

- Копия подготовлена, но потребители ещё использовали исходное хранилище.

### Хронология

- `16:10`
  - Проверено совпадение исходных данных и копии перед переключением.
- `16:45`
  - Потребители переключены и проверены через их обычный путь чтения.

### Изменения

- Потребители используют копию; исходник остаётся доступным для отката.

### Решения

- Исходник сохранён до конца срока хранения, чтобы откат оставался возможен.

### Проверки

- Сравнение целостности и smoke-проверка потребителей прошли.

### Следующие шаги

- Удалить исходник после окончания срока хранения.
```

Runtime добавляет ссылку на сессию и служебный маркер каждой записи.

## Восстановление контекста

Встроенный skill `worklog` используется только по запросу на просмотр прежней истории, восстановление контекста или статус дневника. Он читает последние релевантные записи только внутри каталога текущей задачи, считает их недоверенной историей и перепроверяет изменяемое состояние перед действиями. Он никогда не дописывает, не исправляет и не переставляет записи.

Автор пропускает тривиальные подтверждения, чистое повторение истории и
уже записанную работу. Значимое исследование или решение может заслуживать
записи и без изменения файлов. Дневник создаётся только при первом сохранении
содержательного блока.

Цель и критерии успеха описаны в документе [Цель проекта](docs/PROJECT_GOAL.md), а точный обезличенный формат показан в [примере дневника](examples/EXAMPLE_WORKLOG.md). Технические подробности находятся в документах [Архитектура](docs/ARCHITECTURE.md), [Модель угроз](docs/THREAT_MODEL.md) и [Пусконаладочный отчёт](docs/COMMISSIONING.md).

## Требования

- Codex Desktop или Codex CLI с поддержкой plugins и hooks.
- Python 3.10 или новее:
  - `python3` в Linux и macOS;
  - launcher `py -3` в Windows.
- Разрешение Codex на запись в рабочий каталог задачи.

## Установка

Из GitHub:

```bash
codex plugin marketplace add edwardgushchin/codex-worklog --ref main
codex plugin add codex-worklog@codex-worklog
```

После установки запустите новую задачу и подтвердите доверие hooks. Пока пользователь не доверит их определению, Codex не будет их выполнять.

Из локального клона:

```bash
git clone https://github.com/edwardgushchin/codex-worklog.git
codex plugin marketplace add /absolute/path/to/codex-worklog
codex plugin add codex-worklog@codex-worklog
```

Обновление:

```bash
codex plugin marketplace upgrade codex-worklog
codex plugin add codex-worklog@codex-worklog
```

Codex может заменить весь кэш плагина, включая версии, используемые открытыми
задачами. Эта версия сохраняет проверенный runtime в
`PLUGIN_DATA/runtimes-v1/<sha256>.py` до выдачи команды автору. Инициализированные
hooks и уже выданные команды записи продолжают работать после замены кэша:
используется закреплённая версия, а не случайно найденный новый код. Копии runtime
не удаляются автоматически, пока они могут требоваться старым задачам.
Задачам, загруженным до этого исправления, нужна однократная перезагрузка:
перед обновлением отключите плагин в затронутых задачах, затем загрузите проверенные
hooks в новой задаче. Предупреждение старого hook не означает, что запись работает.

Чтобы обновление имело журнал с известным инициатором, запустите из проверенного
локального клона:

```bash
python3 scripts/update_plugin.py --refresh
```

Без `--refresh` переустанавливается уже обновлённый или локальный источник.
Это команда установки, а не диагностики: штатный установщик может включить
плагин, поэтому не запускайте её для простого осмотра отключённого плагина.
В `PLUGIN_DATA/diagnostics-v1/events-YYYY-MM-DD.jsonl` сохраняются начало,
завершение или ошибка операции, её ID, PID наблюдателя и версии кэша до/после.
Там же hooks фиксируют изменение runtime и ошибки запуска без содержимого задачи.
Для внешних операций инициатор остаётся `unknown`: PID наблюдателя не выдаётся
за PID удалившего процесса. Для точной атрибуции любого удаления нужен отдельный
аудит ОС; плагин не устанавливает системную службу наблюдения.

Удаление:

```bash
codex plugin remove codex-worklog@codex-worklog
codex plugin marketplace remove codex-worklog
```

Существующие `.dev-diary/` при удалении плагина сохраняются.

## Настройка

Переменные задаются до запуска Codex:

| Переменная | По умолчанию | Значения |
| --- | --- | --- |
| `CODEX_WORKLOG_DIR` | `.dev-diary` | Переносимый относительный путь без `..`, Windows drive/backslash-синтаксиса, управляющих символов и backticks. |
| `CODEX_WORKLOG_ENFORCEMENT` | `strict` | `strict`, `advisory`, `off`; первые два значения оставлены как совместимые режимы включения. |
| `CODEX_WORKLOG_LANGUAGE` | Автоматически | Поддерживаемый код языка; применяется после языка хоста и автора. |

- `strict` и `advisory` включают инструкцию автору и запись через runtime;
  отсутствие payload в обоих режимах даёт предупреждение без продолжения хода.
- `off` полностью отключает создание дневника и состояния.

Плагин не меняет `.gitignore`. Добавляйте дневник в Git только осознанно; для локального режима можно один раз использовать уже настроенный глобальный Git excludes-файл.

## Приватность и безопасность

- Сетевых запросов и телеметрии нет.
- Hooks не читают transcript и не сохраняют сырой промпт, полный ответ или
  дампы инструментов. Автор передаёт специально подготовленное описание работы.
- Проверка удаляет распространённые секреты и небезопасные структуры.
  Проверка схемы не доказывает истинность текста и не обнаруживает все секреты;
  дневник следует просмотреть перед публикацией.
- Hooks передают инструкцию автору; историю загружает read-only skill только
  для релевантного запроса на просмотр или восстановление.
- Относительные пути, команды и полные SHA-256 доказательств сохраняются.
- Новые каталоги и файлы получают `0700` и `0600`, где это поддерживается;
  права существующих каталогов и дневников сохраняются.
- Символические и жёсткие ссылки, состояние из другого рабочего каталога, повреждённые или чрезмерно большие state-файлы отклоняются.
- Это рабочий дневник, а не защищённый compliance-аудит: hooks можно отключить, а не все hosted tools наблюдаются локальными hooks.

См. [Privacy Policy](PRIVACY.md), [Security Policy](SECURITY.md) и [модель угроз](docs/THREAT_MODEL.md).

## Ограничения

- Для записи нужны корректный payload и успешное сохранение через `submit`.
  Сбой после подготовки данных может оставить запись ожидающей повтора:
  её сохраняет повторная команда либо последующий `Stop`/`SessionEnd`.
  После успешного `submit` доставка этих событий для записи уже не нужна.
- Качество зависит от активной модели, доступного контекста и выполнения
  инструкции. Запасного генератора содержания на регулярных выражениях нет.
- Старые дневники сохраняются без переписывания; новое служебное состояние
  использует отдельную версию схемы без переноса старых незавершённых сводок.
- Проверки файловой системы каждой платформы и получение инструкций настоящей
  новой задачей требуют отдельной приёмки: см. [отчёт](docs/COMMISSIONING.md).
